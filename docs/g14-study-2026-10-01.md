# GA402RK physical study, 2026-10-01

This is an ongoing physical investigation. It does not establish an optimal
battery preset or a safe sustained gaming power/temperature envelope.

Machine: GA402RK, BIOS 319, Ryzen 9 6900HS / Radeon 680M (`1002:1681`), RX 6800S
(`1002:73ef`). Running Arch kernel 7.1.4-1-g14; installed stock kernel
7.2.7-arch1-1, Mesa/RADV 26.2.3, asusctl 6.5.0. External display physically
reported Dell S2722DC, 2560x1440, 60/75 Hz; initially active at 59.951 Hz.
Internal panel reports 2560x1600, 120 Hz. Ambient temperature was not measured.

## Verified faults and cleanup

- asusd and PPD were both active. asusd's Balanced configuration requests
  BalancePower, while the live EPP was balance_performance. Stopping PPD and
  reapplying ASUS Balanced produced balance_power. This verifies ownership
  contention; it does not quantify the battery benefit.
- Cardwire, LACT and System76 scheduler were also active. They were stopped and
  removed. asusd/asus-shutdown/switcheroo-control remain enabled. PPD/tuned are
  masked to prevent accidental activation. The unused zephyrusctl CLI/timer/
  service, RyzenAdj and Ryzen SMU DKMS driver were backed up and removed.
- The inherited VK_ICD_FILENAMES listed old split Radeon JSON files which no
  longer exist. Vulkan initialization failed. With that variable removed, RADV
  enumerated both actual GPUs. The stale .bashrc overrides and global iGPU
  selector were removed. Already-running applications may retain inherited
  variables until restarted.
- GRUB now selects the installed stock kernel for the next boot. The current
  patched kernel remains available as a fallback. Stock-kernel runtime behavior
  has not yet been tested; the image and in-tree asus-armoury module exist.
- UWSM is installed. Zephyrus has standard user units bound to the graphical
  session. The generated unit passed systemd verification. Both KDE and
  Hyprland login entries remain available through the existing SDDM. Actual
  UWSM login/logout remains a separate validation step.

Original ASUS configuration, removed custom controls, graphics overrides, mpv
configuration and GRUB files are backed up under
`/var/lib/system-g14-study/2026-10-01/` (root-only). Detailed local evidence is
under `~/.local/state/system/g14-observations/2026-10-01-study/`; raw identifiers
and home paths are deliberately not copied into this public record.

## Measurements

After removing competing controls, a 120-second idle record collected 24
samples at five-second intervals. CPU Tctl peaked at 51 C, the RX 6800S was
suspended in every sample, and battery flow was zero because AC was connected.
An open render-node descriptor alone does not prove the GPU is consuming power.

The battery reported 40.804 Wh remaining, 49.949 Wh full capacity and 76 Wh
design capacity: approximately 65.7% of design capacity. It was capped near 80%
and on AC. The zero cycle counter is only the firmware's reported value.

Firmware discovery advertised ppt_apu_sppt 15..80 (current/default 80), and
ppt_platform_sppt 30..115 (current/default 115). Custom fan curves and ASUS
profile tuning were disabled. Disabled legacy tuning groups were later cleared
from the live ASUS configuration after backup; AC Balanced/battery Quiet and
linked EPP policy were preserved and rechecked. No PPT value, curve, boost or temperature ceiling
was selected from these ranges. Historical RyzenAdj readback showed 125 W fast/
STAPM, 100 W slow and 93 C Tctl limits; it cannot establish whether those were
factory settings or residual experiment state without a clean boot comparison.

Playback uses a generated 10-second H.264 1920x1080/24 test pattern, looped for
short checks. These AC checks validate rendering/decoding, not movie endurance
or image quality across codecs. CPU sampling uses k10temp; power1_input is the
APU's reported PPT, not wall or battery consumption. A stop guard at 82 C limits
the playback experiment; it is not a production thermal controller.

The original forced Vulkan setup could not render with the stale ICD override.
A standard configuration used VA-API, ran for 120 seconds, peaked at 52.25 C and
reported no dropped frames. With ICD discovery repaired, Vulkan Video worked.
The old shader configuration versus standard scaling each ran for 120 seconds:
median reported PPT was 19.194 versus 19.206 W, with no dropped frames. This
comparison does **not** establish a shader power saving. A subsequent fixed Vulkan-renderer test with `hwdec=vaapi` fell back to
software decoding, so that pairing is not the selected configuration.

The final comparison used standard scaling, the same window/clip, fixed ASUS
Balanced/balance_power, AC, external 60 Hz and internal 120 Hz panels. Four
120-second runs in reverse order each collected 60 samples:

| Path | Median reported APU PPT | Mean reported APU PPT | RX 6800S active samples | Dropped frames |
| --- | ---: | ---: | ---: | ---: |
| OpenGL / VA-API, first | 7.019 W | 7.549 W | 0/60 | 0 |
| Vulkan / Vulkan Video, first | 17.044 W | 16.865 W | 60/60 | 0 |
| Vulkan / Vulkan Video, repeat | 18.051 W | 17.618 W | 60/60 | 0 |
| OpenGL / VA-API, repeat | 7.057 W | 9.411 W | 2/60 | 0 |

The two active samples on the final OpenGL run were at startup after Vulkan;
the dGPU suspended after four seconds. A short debug replay confirmed that
libplacebo selected the RX 6800S as the Vulkan rendering device. The OpenGL
path used VA-API and allowed that GPU to remain asleep. CPU Tctl stayed below 60 C in these playback runs.
Other desktop applications remained open; package hooks briefly refreshed
firmware metadata in the background. These are short practical desktop
comparisons, not quiescent laboratory or battery measurements. The repeated
median and runtime-PM behavior support the native OpenGL/VA-API preference for
this tested H.264 path. No runtime-hours claim is derived from APU PPT.

Implementation: common mpv uses `hwdec=auto` and optional shader profiles. Only
GA402RK provisioning adds `gpu-api=opengl`, allowing the native player to choose
VA-API with the current Mesa stack. Other hardware keeps automatic rendering.
The same preference is applied to the live user configuration. Test other codecs,
4K playback, subtitle-heavy scenes and the actual battery movie before extending
this conclusion.

Two bounded vkmark Phong trials used a 1920x1080 Wayland window, ASUS Balanced
and AC. Stop guards were CPU Tctl 82 C, dGPU edge 75 C and junction 85 C. The
first offload request still selected the 680M: it reached the CPU stop guard
after 100.7 seconds (one-second recorded peak 81.875 C). Both fans responded,
peaking at 3100/3200 RPM, and temperatures fell after stopping. The recorder
was interrupted during its cooldown wait; its CSV is retained as partial data.

The second trial explicitly selected the RX 6800S using Mesa's native
**per-process** `MESA_VK_DEVICE_SELECT=1002:73ef!`; vkmark's device header
confirmed `73ef`. It completed 120 seconds, with CPU Tctl peak 68.375 C, dGPU
edge 66 C, junction 74 C, reported dGPU power peak 18 W and fan peaks
2100/2300 RPM. This is a light graphics smoke check, not a representative
combined CPU/GPU gaming load. The integrated trial's stop is evidence against
claiming that profile selection alone guarantees safe temperatures. No global
GPU selector, thermal controller or benchmark dependency was installed by
these trials; the temporary vkmark/assimp packages were removed afterward.

Zephyrus's actual actions selected Quiet/power and restored Balanced/balance_power
successfully. Its old saved Balanced Cardwire Smart field was backed up and
removed. The final native Zephyrus package (20260930.g2724e41-4) built and was
installed from the pinned public archive plus the checksummed review patch.
The legacy pacman firmware/AppImage update hooks were removed after backup;
firmware updates remain explicit and only the standard metadata refresh timer
is enabled. No firmware update was available/applied during the package hook.

Fresh GA402RK provisioning seeds the native ASUS configuration with Balanced
on AC, Quiet on battery and linked native EPP, matching the observed profile
baseline. Upstream otherwise defaults to Performance on AC. Charge limits
retain upstream's 100% default until the user changes them; the live user's
existing 80% cap remains. ASUS's configuration directory is preserved across
rebuilds so native profile, charge-limit, lighting and fan settings survive.
The seed has empty tuning groups and applies no custom power or fan limits.

## What is still required

The one-hour battery playback and gaming shutdown are unresolved until measured
under their actual conditions. Needed: internal-panel-only unplugged playback
with a fixed player/movie/brightness/refresh rate, and the game/scene that triggers
the shutdown on AC with fan, CPU and GPU junction readings. Use the observer for
at least 30 minutes of playback and 10–15 minutes of a bounded game comparison.
Stop early on abnormal temperatures or fan response rather than reproduce a
hard shutdown. Validate stock-kernel boot/suspend and UWSM login/logout too.

No full installer/VM suite was repeated. Focused graph, home fallback, private
hydration, Zephyrus machine/settings/session tests, QML Settings/battery smoke
checks and package-source patch checks cover the changes made in this follow-up.

## Follow-up controls and unresolved gaming shutdown

The owner reports shutdowns during demanding Steam games on AC, around a
reported 93 C; sensor identity and simultaneous GPU junction/fan readings are
unknown. This is not a resolved thermal result. The latest audit found asusd
active, PPD/tuned masked and the removed writers absent. KDE PowerDevil was
inactive in Hyprland, so no KDE runtime claim follows. The stock-kernel reboot
remains pending. The previous boot's kernel log had no conclusive thermal
shutdown message in the inspected matches.

Zephyrus now supplies a manual CPUFreq boost toggle using a scoped root-owned
polkit helper and per-app GPU launches using switcheroo-control identities.
No new power policy daemon or firmware limit was added. Boost action routing,
invalid-input rejection, UI state and actual child launch environment were
verified without changing the real CPU boost state or starting a GPU workload.
The live discovery identified both the 680M and RX 6800S. The old zephyrusctl
`1002:73ff` selector does not match this dGPU (`1002:73ef`).

The user-manager still held a stale integrated-GPU Vulkan selector after its
persistent source was removed. Cleanup affects future manager-launched
processes; already running processes need a fresh login. The owner chose
`generic-high` as mpv's default; provisioning now records that preference too.
This shader preference is not evidence of a thermal improvement or regression.
